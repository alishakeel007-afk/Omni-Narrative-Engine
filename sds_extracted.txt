Chapter 3: Design and Architecture
This chapter presents the high-level architectural design of Omni-Narrative Engine, describing how the web interface, story state, AI services, voice generation, background music context, and video studio modules interact. The design focuses on modularity, secure API usage, responsive user interaction, and extensibility for future multimedia generation components
3.1 System Architecture Overview
The Omni-Narrative Engine is an AI-powered cinematic storytelling platform that allows users to create interactive stories, guided adventures, custom scene-by-scene scripts, character dialogues, voice narration, background music, and video-ready previews. The system is implemented as a Next.js web application with server-side API routes that integrate with external AI services.
3.1.1 Purpose of Architectural Overview
The purpose of this overview is to describe how the major modules of Omni-Narrative Engine cooperate as one system. It identifies where each feature resides, how frontend screens communicate with backend API routes, how external AI services are called securely, and how story data is preserved between steps.

3.3 Architecture Style / Pattern
The system adopts a Client-Server Architecture with a Layered Backend pattern. The client-side interface collects user input, displays workflow stages, and shows generated content. Server-side API routes own sensitive operations such as authentication and calls to Gemini, Groq, Deepgram, and background music providers.
3.3.1 Justification for Choosing Client-Server Architecture with Layered Backend
Clear separation of concerns between UI screens and provider/backend logic.
API keys remain in .env.local and are never sent to the browser.
AI routes can later be moved to independent services without redesigning the frontend workflow.
Guided Mode, AI Story Studio, audio generation, and preview logic are separated into dedicated screens and storage helpers.
Groq fallback protects story and dialogue generation when Gemini returns high-demand or unavailable responses.
Real image generation, vector memory, and video rendering can be added as separate backend modules.

3.5.4 Data Security
The Omni-Narrative Engine ensures full protection of sensitive user data, authentication credentials, AI provider keys, and generated storytelling media through the following security mechanisms:
Data Security
The system protects user account information and authentication data by applying secure password handling and encrypted communication practices.
Passwords are hashed using bcryptjs before storage. 
bcryptjs automatically applies salting, which helps prevent attackers from easily reversing stored passwords. 
The system never stores plain-text passwords in the database. 
Secure communication is maintained through HTTPS/TLS, ensuring that data exchanged between the client, Next.js server, and external AI APIs remains protected during transmission. 
Authentication
The system uses token-based authentication to verify users and manage secure sessions.
JWT authentication is implemented using the jose library. 
After successful login, the session token is stored in a secure httpOnly cookie. 
httpOnly cookies help prevent client-side scripts from directly accessing session tokens. 
Next.js Middleware acts as a strict session guard for private pages. 
Time-limited cryptographic hashes are used for password reset tokens to reduce the risk of replay attacks. 
Access Control
Access control is applied to ensure that only authorized users can access private workflow pages and protected system features.
ProtectedRoute prevents unauthorized users from opening private frontend pages. 
Next.js Middleware protects important routes such as dashboard, setup, story, audio generation, and video preview pages. 
Server-side API route protection helps prevent unauthorized access to costly AI generation endpoints. 
Prisma ORM is used for safe database operations and helps isolate user account-related queries. 
API Key and Provider Security
The system keeps all external AI service credentials secure by handling them only on the server side.
Provider keys for Gemini, Groq, Deepgram, and background music services are read only from server environment variables. 
Sensitive credentials are stored in .env.local and are not exposed to the frontend. 
Frontend pages never call third-party AI providers directly. 
All AI requests are routed through secure Next.js API routes such as /api/video/generate, /api/video/tts, /api/tts, and /api/background-music. 
Privacy and Infrastructure Security
The project reduces unnecessary exposure of user creative data by keeping active drafts on the client side where appropriate.
Active story drafts, video drafts, scenes, dialogues, and generation statuses are stored using browser localStorage. 
This approach reduces unnecessary server-side storage of the user’s personal creative work. 
Only required data is sent to API routes during AI generation requests. 
Environment isolation ensures that API keys and private configuration values remain separate from public frontend code.

4.1 Project Methodology & Algorithms
4.1.1 Project Methodology
The implementation follows an iterative prototype methodology. Core workflows were built and refined in stages: frontend navigation, authentication, guided story generation, custom story builder, dialogue generation, voice generation, background music, video preview placeholder, fallback reliability, and state persistence.
4.1.2 Methodology Phases (Detailed Workflow)
The Omni-Narrative Engine development workflow is organized into the following major stages:
Requirement Analysis: 
Functional and non-functional requirements were identified for an AI-powered multimedia storytelling system. The main requirements included user authentication, guided story creation, custom story building, AI-generated narrative scenes, character dialogues, voice generation, background music generation, story memory, history tracking, draft persistence, and video preview flow.
Frontend and UI/UX Development: 
The cinematic frontend of the system was developed using Next.js, React, TypeScript, and Tailwind CSS. The interface was designed with a dark cinematic theme to match the storytelling purpose of the system. Major screens were developed, including:
Landing page 
Dashboard 
Story mode selection screen 
Story setup screen 
Story play screen 
Story memory screen 
Story history screen 
Story export screen
The purpose of this phase was to provide users with a smooth and immersive storytelling experience.
Authentication and Route Protection:
The login and signup backend was implemented using Prisma SQLite, bcryptjs password hashing, JWT sessions, and protected routes. The authentication module allows users to create accounts, log in securely, maintain sessions, and access only authorized workflow pages.
This phase included:
User signup 
User login 
Password hashing using bcryptjs 
JWT-based session handling using jose 
Middleware-based route protection 
ProtectedRoute handling for private frontend pages 
Guided Video Studio Development: 
The Guided Video Studio module was implemented to allow users to generate a story-based video workflow through guided steps. In this mode, the user provides a story idea and the system generates structured story content using AI.
This phase included:
Story idea input 
Gemini-based story generation 
Scene and dialogue review 
Character dialogue organization 
Deepgram voice generation 
Background music generation 
Preview screen for generated story content 
The purpose of this phase was to support users who want the system to guide the storytelling process automatically.
AI Story Studio Custom Mode Development: 
The AI Story Studio custom mode was implemented for users who want more creative control over their story. In this workflow, users can define their own story structure, characters, scenes, dialogues, and scene progression.
This phase included:
Multi-character setup 
Character name, role, personality, and voice style input 
Scene-by-scene story builder 
AI scene suggestions 
AI dialogue generation 
Editable character dialogues 
Audio generation controls 
Custom preview routing
This module gives users more freedom compared to Guided Mode because they can edit and shape the story manually before generating audio and preview content.
AI Provider Integration and Fallback Handling:
AI provider integration was added to support story generation and dialogue generation. Gemini was used as the main provider for story-related AI generation. Fallback logic was also added using Groq when Gemini returns high-demand errors such as 503 service unavailable or when Gemini does not return usable output.
This phase included:
Gemini provider integration 
Groq fallback handling 
Response validation 
Error handling for unavailable AI services 
User-friendly fallback messages
The purpose of this phase was to improve system reliability and prevent the workflow from stopping when one AI provider fails.
Draft Persistence and Regeneration Handling: 
Draft persistence was added to prevent users from losing progress during the story creation process. The system saves active story drafts, video drafts, dialogue edits, audio status, and preview status using browser localStorage.
This phase included:
Story draft saving 
Video studio draft saving 
Back and edit controls 
Regeneration warnings after story or dialogue edits 
Audio status tracking 
Music generation status tracking 
Preview routing after completion
This ensures that users can move backward, edit previous content, and continue the workflow without losing their work.
Testing and Validation: 
Manual testing was performed to verify that the major system workflows function correctly. The system was tested across authentication, protected routes, story setup, guided video generation, custom story building, AI fallback handling, audio generation, music generation, and draft persistence.
Testing included:
Unit testing of validation functions 
Authentication workflow testing 
Protected route testing 
Story setup validation 
Guided Video Studio workflow testing 
AI Story Studio workflow testing 
API response validation 
Draft persistence testing
Back/edit workflow testing 
Deployment Preparation:
The project is currently prepared for local development and testing using the Next.js development server. Production deployment has not been fully performed yet. In future deployment, the application can be hosted on platforms such as Vercel, with provider API keys stored securely in server-side environment variables
Future deployment may include:
Vercel deployment for Next.js frontend and API routes 
Cloud database replacement for SQLite \
Secure production environment variables 
Scalable AI API route handling 
Video rendering backend integration using tools such as Remotion or FFmpeg
4.1.3 Algorithms
The algorithms presented below are aligned with the implemented SDS phase and focus on the core system operations.
4.2.1 Algorithm 1 – Custom Story Generation Routing
PROCEDURE HandleStoryStart(setup)
1.  IF setup.mode = "custom" THEN
2.      rawIdea <- setup.startingIdea
3.      Validate(rawIdea)
4.      prompt <- BuildStoryPrompt(rawIdea, setup.genre, setup.mood)
5.      scene <- GenerateSceneWithLLM(prompt)
6.  ELSE
7.      scene <- GenerateGuidedOpening(setup)
8.  END IF
9.  SaveCurrentScene(scene)
10. RenderStoryScreen(scene)
END PROCEDURE
4.2.2 Algorithm 2 – Scenario-to-Video Generation
PROCEDURE GenerateVideoScenario(request)
1.  scenario <- Validate(request.scenario)
2.  genres <- NormalizeList(request.genre)
3.  tones <- NormalizeList(request.tone)
4.  prompt <- BuildGeminiMoviePrompt(scenario, genres, tones)
5.  script <- CallGemini(prompt)
6.  scenes <- NormalizeScenes(script.scenes)
7.  voices <- AssignCharacterVoices(scenes)
8.  IF request.includeAudio = TRUE THEN
9.      FOR each dialogueLine IN scenes
10.         audio <- GenerateDeepgramAudio(dialogueLine)
11.         AttachAudio(dialogueLine, audio)
12.     END FOR
13. END IF
14. Return VideoGenerationResponse
END PROCEDURE
4.2.3 Algorithm 3 – Background Music Context Generation
PROCEDURE GenerateBackgroundMusic(scene)
1.  mood <- scene.backgroundMusicMood OR scene.mood
2.  prompt <- scene.soundDesign OR scene.audioMoodPrompt
3.  IF BG_MUSIC_API_KEY and BG_MUSIC_API_URL exist THEN
4.      track <- CallMusicProvider(mood, prompt)
5.  ELSE
6.      track <- ReturnConfiguredFallbackTrack()
7.  END IF
8.  RenderMusicPlayer(track)
END PROCEDURE

4.3 Authentication and Security
4.3.1 Authentication
Users register and log in using backend API routes. Credentials are validated, stored with hashed passwords, and authenticated sessions are maintained through JWT tokens. Protected pages are guarded so unauthenticated users are redirected to login.
4.3.2 Encryption
The application hashes passwords using bcryptjs. API keys are kept in .env.local and used only inside server-side API routes. Deployment should use HTTPS/TLS to protect tokens and requests in transit.
4.3.3 Attack Prevention
- Password hashing prevents plaintext password exposure.
- Server-side API routes prevent direct exposure of AI provider keys.
- Input validation blocks incomplete generation requests.
- JWT middleware reduces unauthorized access to dashboard and studio pages.
- Fallback errors are reported without exposing secrets.
4.3.4 Additional Security Measures
Recommended production measures include rate limiting AI endpoints, CSRF-aware cookie settings, audit logging, database backups, stricter request schemas using Zod, and deployment secret management.
4.3.5 Security Testing Results
Current verification includes TypeScript build validation, successful route compilation, login/signup correction, and protection of private routes through the implemented middleware. Formal penetration testing is pending.

4.6 Deployment
4.6.1 Web Application Deployment
The project is built as a Next.js application and can be deployed to a Node-compatible platform such as Vercel, Render, Railway, or a VPS. Production build is generated through npm run build and served with npm run start.
4.6.2 Database Deployment
The current development database is SQLite through Prisma. For production, PostgreSQL is recommended so authentication and activity logs can scale beyond a local file database.
4.6.3 External API Integrations
Gemini, Groq, Deepgram, and music provider keys must be configured as environment variables on the deployment platform. No keys should be placed in frontend code or public repositories.
