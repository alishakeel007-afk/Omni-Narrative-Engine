Chapter 2: Requirement Analysis
This chapter presents a detailed analysis of the functional and non-functional requirements of the Omni-Narrative Engine system. It explains the user needs, system goals, operational expectations, and technical limitations identified during the problem analysis and scope definition stages. This analysis provides the basis for the design and development of the proposed system, ensuring that each module and feature contributes effectively to the main objective of the project - to generate an interactive, AI-driven multimedia storytelling experience in which narrative text, visuals, sound, and user decisions work together in a coherent and engaging manner. The chapter also helps define what the system must do, how it should perform, and what constraints must be considered to make the final product practical, usable, and academically achievable.
2.1 User Classes and Characteristics
The Omni-Narrative Engine is designed to serve multiple categories of users, each with different roles, responsibilities, permissions, and levels of interaction with the system. The following table describes the main user classes expected for this application and explains their relevant characteristics.
Table 1 User Classes and Characteristics
Feature (derived from UI)
Functional Requirement (FR-ID: Statement)
User Class
Description
User / Player
A User or Player represents the primary individual who accesses and uses the Omni-Narrative Engine to create, experience, and interact with AI-generated stories. This user starts a new story session by selecting inputs such as genre, world setting, narrative style, character profile, difficulty level, emotional tone, and other story preferences. During the session, the user reads generated narrative text, views scene images, listens to generated or selected audio, and makes decisions that influence the next events in the story. The user may also manage inventory, track character state, review story memory, view past scenes, save progress, and continue incomplete sessions later. This class is expected to have minimal technical knowledge and should be able to use the system through a clear, engaging, and easy-to-understand interface. Since the system is mainly built for this class, the user interacts with most functional modules, including story generation, multimedia rendering, choice management, memory tracking, and session persistence.
Administrator
The Administrator is responsible for supervising the overall operation and maintenance of the Omni-Narrative Engine. This user manages system settings, monitors generated content quality, checks system performance, reviews user activity, handles account-related issues, and ensures that the system remains functional and reliable. The administrator may also manage content rules, review logs, oversee data storage, maintain service availability, and coordinate with developers when technical problems occur. This role requires moderate technical knowledge, especially in areas related to configuration management, system monitoring, database handling, and operational support. Although a fully developed administrative dashboard may be considered as future work, this role remains important for controlling and maintaining the system environment.

2.1.2 Requirement Identifying Technique
The Mockup-Based Requirement Analysis technique has been used to identify and document the functional requirements of the Omni-Narrative Engine. This technique is based on a user-centered approach in which system requirements are extracted by studying the expected user interface screens and the interactions that take place on them. It allows early understanding of system behavior by representing how users will move through the platform and how each module should respond to user input. Since the Omni-Narrative Engine is an interactive multimedia storytelling system, this technique is especially suitable because many of its requirements are directly linked to user actions such as selecting story settings, starting a session, making choices, viewing generated scenes, listening to audio, managing story memory, and saving progress. Each mockup represents a meaningful user interaction point, and from each screen, the related system functions can be identified and documented clearly.
2.1.2.1 Steps Followed
1. Key system features were identified and divided into specific mockup screens. The main features of the Omni-Narrative Engine were first identified from the approved project scope and then separated into individual interface screens. These screens represent the actual flow of user interaction, such as login or access, story setup, genre selection, scenario selection, character customization, story confirmation, active story session, choice selection, story history, memory view, and save or resume options.
2. Each screen was designed to visualize the interface layout and user workflow. Every mockup was prepared to show how the user would interact with the system at that stage. The purpose of this step was to map the navigation flow, input controls, displayed information, and transitions between one part of the story process and the next. This helped in understanding how the storytelling experience would be structured from beginning to end.
3. Each interactive element was examined to derive expected system behavior. All important interactive elements on the mockups, such as buttons, text areas, dropdowns, selection panels, media controls, progress indicators, save options, and choice cards, were analyzed carefully. From this analysis, the expected response of the system was determined.
4. Each identified behavior was documented as a Functional Requirement with a unique identifier. After identifying the expected behavior of each interaction, the behavior was converted into formal functional requirements. Each requirement was assigned a unique identifier, such as FR-1.1, FR-1.2, and so on, to make the requirements easier to reference in later sections of the SRS, during design, and during implementation.
5. All derived requirements were organized into structured requirement tables. The identified functional requirements were then arranged in clear and systematic tables so that each system behavior could be presented in an organized way. This structure improves readability and makes it easier to connect each requirement with the relevant user action or system module.
6. Business rules and system constraints were added where necessary. Wherever required, additional rules were included to define validation conditions, access restrictions, system limitations, session handling conditions, and consistency requirements. In the case of the Omni-Narrative Engine, these rules may include input validation for story settings, restrictions on guest access, conditions for saving sessions, content generation constraints, and continuity rules to maintain story coherence across scenes.
2.2 Backend Process Requirements
While mockups are useful for representing the frontend behavior of the Omni-Narrative Engine, the system also contains several important backend processes that are not directly visible through interface screens. These processes are necessary for handling story generation, session continuity, multimedia synchronization, state tracking, memory management, authentication, and system reliability. To properly represent these internal operations, an event-response table has been developed. 2.3 Non-Functional Requirements
The Non-Functional Requirements are:
2.3.1 Performance
PER-1: The system shall generate and display the initial narrative response for a new story session within an acceptable response time under normal operating conditions.
PER-2: The system shall update scene-generation progress indicators in real time or near real time while narrative, image, and audio components are being processed.
PER-3: The Story Hub , saved sessions view, history page, memory page, and player state page shall load within a short and usable time after a valid user request.
PER-4: The system shall process user choice submission and initiate next-scene generation without unnecessary delay.
PER-5: The system shall support smooth retrieval of saved sessions, story history, memory records, and player state without noticeable interruption to the user experience.
2.3.2 Accuracy and Consistency
ACC-1: The system shall generate story content that remains consistent with the user’s selected genre, scenario, tone, difficulty, and character configuration.
ACC-2: The system shall maintain continuity of key events, characters, locations, player state, and active story threads across scene transitions.
ACC-3: The system shall ensure that displayed progress values, scene numbers, attribute values, and session details match the actual stored session state.
ACC-4: The system shall record user choices accurately and use them as valid input for future scene generation.
ACC-5: The system shall preserve consistency between visible story memory and the internal context used by the narrative engine wherever applicable.
2.3.3 Usability
USA-1: A new user shall be able to understand the basic purpose of the system and begin a story session with minimal guidance.
USA-2: The system shall provide a clear and step-based story setup flow so that users can configure genre, scenario, tone, difficulty, and character without confusion.
USA-3: Important user actions, such as starting a new story, resuming a session, selecting a choice, and reviewing context pages, shall require only a small number of clear interactions.
USA-4: The interface shall use readable text, clear labels, meaningful buttons, and organized layout structures to support ease of use.
USA-5: The system shall present story-related context, such as memory, history, and player state, in a way that is easy for users to understand even during long sessions.
2.3.4 Reliability
REL-1: The system shall remain operational and available for normal use except during planned maintenance or major service interruption.
REL-2: If one multimedia generation component fails, such as image or audio generation, the system shall continue to preserve the narrative session and provide fallback behavior where possible.
REL-3: The system shall preserve saved sessions, story memory, history, and player state so that users can continue their narratives later without major loss of progress.
REL-4: The system shall handle failed API calls, temporary service delays, or incomplete generation states without crashing the user session.
REL-5: The system shall maintain valid session continuity when a user resumes a previously saved story.
2.3.5 Security & Privacy
SEC-1: The system shall require secure authentication for registered users and shall protect account access through validated login procedures.
SEC-2: User credentials shall be stored securely using accepted encryption or hashing practices and shall never be stored in plain text.
SEC-3: The system shall restrict access to saved sessions, story history, memory, and player state so that only the authorized user can access their own data.
SEC-4: Communication between frontend, backend, and integrated services shall occur through secure channels.
SEC-5: Sensitive system credentials, configuration values, and API keys shall be stored securely and shall not be exposed directly in the user-facing interface.
2.3.6 Portability
POR-1: The system shall be deployable in a web-based environment accessible through standard modern browsers.
POR-2: The user interface shall adapt to different screen sizes and resolutions without losing major functionality.
POR-3: The architecture of the system should support future deployment extension to other platforms if required.
2.3.7 Maintainability
MAI-1: The system should be designed in modular form so that major components such as narrative generation, session management, memory handling, multimedia generation, and interface logic can be updated independently.
MAI-2: The codebase should be organized in a way that simplifies testing, debugging, and future enhancement.
MAI-3: The system should support replacement, improvement, or retraining of AI-related modules without requiring complete redesign of the whole application.
MAI-4: Backend services, APIs, and data storage logic should be structured clearly to support maintenance and future scalability.
2.3.8 Accessibility
ACS-1: The interface shall use readable typography, clear contrast, and properly sized controls so that users can interact with the system comfortably.
ACS-2: Buttons, tabs, cards, and navigation controls shall remain easy to identify and select across supported devices.
ACS-3: The system shall organize information in a clear and consistent way so that users can move between story interaction and support pages without confusion.
ACS-4: Progress indicators, labels, and state information shall be presented in a way that is understandable to a broad range of users.
2.4 External Interface Requirements
This section defines the external interface requirements of the Omni-Narrative Engine, including user, software, hardware, and communication interfaces. These interfaces ensure that the system remains usable, modular, connected, and operational across the components involved in interactive story generation and session management.
2.4.1 User Interfaces Requirements
UI-1: The application shall follow an immersive visual theme suitable for AI-driven storytelling, using a dark cinematic interface with contrasting accent colors to support focus and atmosphere.
UI-2: The system shall provide a consistent top navigation structure for important sections such as Story Hub, My Sessions, History, Memory, and Player State.
UI-3: The interface shall present the story setup process as a clear step-by-step flow with visible progress indicators.
UI-4: The system shall use modern, readable typography with clear heading hierarchy and suitable font sizing across major screens.
UI-5: All major screens shall maintain a consistent layout structure with branding, navigation, primary content area, and action controls.
UI-6: The system shall use clear visual indicators for selected options, active tabs, progress states, risk levels, and status conditions.
UI-7: The active story screen shall present narrative content, decision choices, and audio controls in a structured and readable way.
UI-8: The system shall provide context support pages, such as Story History, Story Memory, and Player State, using organized card-based or section-based layouts.
UI-9: The interface shall remain responsive across supported screen sizes so that core features remain accessible on different displays.
UI-10: The system should follow accessibility-aware design principles such as readable contrast, meaningful labels, large enough controls, and simple navigation flow.
2.4.2 Software interfaces
SW-1: The frontend application shall communicate with the backend through defined API endpoints for session control, story generation, and user-related operations.
SW-2: The system shall integrate a narrative generation engine to produce story text based on user setup, previous scenes, and selected choices.
SW-3: The system shall integrate image generation services or modules for producing scene-related visuals where supported.
SW-4: The system shall integrate audio or ambience generation and playback support for narration and atmospheric sound where enabled.
SW-5: The backend shall communicate with the session management module to save, load, and update story session data.
SW-6: The system shall connect with a data storage mechanism for user accounts, saved stories, story history, memory records, and player state information.
SW-7: The system shall support structured request and response formats for data exchange between frontend and backend components.
SW-8: The system should support modular integration of AI-related services so that narrative, visual, and audio generation can operate as separate but coordinated components.
SW-9: Administrative or maintenance-related system monitoring may be supported through protected backend access in future extensions.
SW-10: All software interfaces shall follow secure authentication and authorization practices for protected resources.
2.4.3 Hardware interfaces
The Omni-Narrative Engine does not depend on specialized external hardware devices. Its main hardware interaction is through standard computing devices used to access the application.
HW-1: The system shall operate on standard computing devices capable of running a modern web browser.
HW-2: The system shall rely on the device display for showing story content, generation progress, memory panels, and player state information.
HW-3: The system shall use the device’s audio output hardware for narration and ambient sound playback where such features are enabled.
HW-4: The system shall rely on the device’s input hardware, such as keyboard, mouse, touchpad, or touchscreen, for setup selection and story interaction.
HW-5: The system shall require internet-connected hardware capable of communicating with remote generation and storage services.
HW-6: Future versions may support extended multimedia or device-specific features, but such hardware dependencies are not required in the current scope.
2.4.4 Communications interfaces
The Omni-Narrative Engine communicates with backend services, storage systems, and AI generation components through secure network-based interfaces.
CI-1: The frontend application shall communicate with the backend using secure internet-based communication protocols.
CI-2: Data exchanged between user interface and backend services shall use structured request-response communication.
CI-3: The system shall support communication between the main application backend and narrative generation services for producing story content.
CI-4: The system shall support communication between the main backend and image or audio generation modules when multimedia output is enabled.
CI-5: The system shall transmit authentication and session-related data using secure token-based or session-based mechanisms.
CI-6: Communication between session management, memory management, and storage components shall preserve data consistency for active and saved stories.
CI-7: The system shall support asynchronous processing behavior for long-running generation tasks such as scene creation, visual production, or audio synthesis.
CI-8: The system shall handle temporary communication failure gracefully and should avoid permanent loss of valid story progress.
CI-9: Sensitive communication credentials and API configuration values shall be stored securely and managed outside direct user access.
CI-10: The communication framework shall ensure that protected user data is not transmitted or stored in plain text.
